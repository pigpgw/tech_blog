## 요약

### 브라우저는 메모리를 어떻게 관리하는가?

브라우저의 메모리 관리는 **필요한 만큼 받아서 사용하고, 필요 없어지면 정리하는 과정**입니다. Chrome은 메모리를 한 곳에서 모두 사용하지 않고 역할별로 나누어 사용합니다. 브라우저 프로세스는 탭과 권한을 관리하고, 렌더러 프로세스는 웹 페이지와 JavaScript를 실행하며, GPU 프로세스는 화면과 그래픽을 처리하고, 네트워크 서비스 프로세스는 인터넷 요청을 처리합니다.

페이지를 사용하는 동안에는 각 프로세스가 필요한 데이터와 화면 리소스를 보관합니다. 더 이상 필요하지 않고 애플리케이션도 참조하지 않는 데이터는 JavaScript 엔진이나 브라우저가 정리합니다. 브라우저는 다시 사용할 데이터를 캐시에 저장하지만, 저장 공간이 부족해지면 오래된 캐시부터 제거합니다.

메모리가 부족해지면 브라우저는 캐시를 비우거나 백그라운드 탭을 잠시 멈추고, 필요하면 탭을 다시 열 때 새로 불러오도록 정리할 수 있습니다. 다만 SPA에서는 페이지가 계속 열려 있으므로, 화면에서 사라진 기능의 이벤트 리스너·타이머·WebSocket·Worker는 개발자가 직접 정리해야 합니다.

> **핵심:** 브라우저는 프로세스와 구성요소별로 메모리를 나누어 관리하고, 더 이상 필요하지 않으며 참조도 남아 있지 않은 리소스를 회수합니다. SPA는 페이지와 실행 환경이 계속 유지되기 때문에, 화면에서 사라진 컴포넌트의 이벤트 리스너·타이머·연결이 참조로 남을 수 있습니다. 브라우저는 애플리케이션이 아직 사용하는지 알 수 있는 참조를 임의로 끊을 수 없으므로, 개발자가 컴포넌트의 리소스 생명주기와 cleanup을 직접 관리해야 합니다.

## Deep Dive

### 1. 전체 구조 (3개 층위)

```text
③ 언어 층위   JS 개념 (변수, 객체, 호출 스택)               ← JS 명세
      ↓ 실제 저장은 엔진이 결정
② 엔진 층위   V8이 직접 관리: JS 힙, 코드 영역              ← V8
      ↓ 메모리는 OS에서 받아서 사용
① OS 층위     프로세스: 코드·데이터·힙·mmap (스레드 공유)
              스레드: 스택 (스레드마다 하나)                ← OS
```

- ③은 "어디에 저장하라"를 정하지 않고, ②가 ①에서 받은 메모리 안에 배치한다.
- V8이 관리하는 건 JS뿐이다. DOM, 이미지, GPU, 네트워크 등은 브라우저의 다른 구성요소가 관리한다.

### 2. OS 층위: 프로그램, 프로세스, 스레드

#### 2-1. 프로그램과 프로세스

- **프로그램**: 디스크에 있는 실행 파일 (예: chrome.exe). 메모리 영역을 받지 않는다.
- **프로세스**: 그 프로그램이 실행 중인 인스턴스. **OS가 프로세스마다 독립된 가상 주소 공간을 하나씩 할당**한다.
- 같은 프로그램을 두 번 실행하면 프로세스가 2개 생기고, 각각 코드·데이터·힙·스택을 따로 가지며 서로의 메모리를 직접 볼 수 없다.
- 하나의 프로그램이 자식 프로세스를 만들 수도 있다. 브라우저는 하나의 프로그램이지만 실행 중에는 여러 프로세스로 나뉜다. 처음 뜬 브라우저 프로세스가 렌더러·GPU·네트워크 프로세스 등을 추가로 띄우고, 대부분 같은 Chrome 실행 파일에 실행 옵션(예: `-type=renderer`)만 달리 준 것이다.

```text
chrome.exe (프로그램, 디스크의 파일 1개)
   │ 실행
   ├─ 프로세스 1 (브라우저)  → 자기 가상 주소 공간
   ├─ 프로세스 2 (GPU)       → 자기 가상 주소 공간
   ├─ 프로세스 3 (렌더러 A)  → 자기 가상 주소 공간
   └─ 프로세스 4 (렌더러 B)  → 자기 가상 주소 공간
```

- 여러 프로세스로 나누는 이유
  - 안정성: 한 탭의 렌더러가 죽어도 브라우저 전체와 다른 탭은 유지된다.
  - 보안: OS가 프로세스 간 메모리를 격리하고, 렌더러는 샌드박스로 권한(파일 접근 등)을 제한한다.
  - 성능: 여러 CPU 코어에서 병렬 실행되고, 한 탭의 무거운 JS가 다른 탭에 미치는 영향이 적다.
- 트레이드오프: 프로세스마다 독립된 메모리와 런타임(V8 등)을 갖기 때문에 메모리 사용량이 늘어난다.

#### 2-2. Chrome의 프로세스 구조

```text
브라우저 프로세스 (1개)      ← 주소창, 탭 UI, 프로세스 관리, 권한
GPU 프로세스 (1개)           ← 모든 탭의 그래픽 처리
네트워크 서비스 (1개)        ← 모든 탭의 네트워크 요청 처리
기타 유틸리티 프로세스들      ← 오디오 등

렌더러 프로세스 A  ← 탭 1 (a.com)
렌더러 프로세스 B  ← 탭 2 (b.com)
렌더러 프로세스 C  ← 탭 3 (c.com)
```

| 프로세스        | 개수            | 역할                                                                    |
| --------------- | --------------- | ----------------------------------------------------------------------- |
| 브라우저        | 전체 1개        | UI, 프로세스 관리                                                       |
| 렌더러          | 탭(사이트)마다  | HTML/CSS 파싱, DOM·CSSOM, 레이아웃, 페인트, **JS 실행(V8)**, Web Worker |
| GPU             | 전체 1개 (공유) | 모든 렌더러의 그래픽 요청 처리, 최종 화면 합성                          |
| 네트워크 서비스 | 전체 1개 (공유) | 모든 렌더러의 네트워크 요청 처리                                        |

- 렌더러 프로세스는 특수한 것이 아니라 **웹 페이지 콘텐츠를 실제로 처리하는 역할의 프로세스**를 부르는 이름이다.
- 웹 페이지의 JavaScript는 해당 페이지를 처리하는 렌더러 프로세스 안의 **V8 엔진**에서 실행된다.
- 기본적으로 탭이나 사이트 콘텐츠는 렌더러가 담당하고, GPU·네트워크는 여러 탭의 요청을 공유해서 처리한다. 렌더러가 "이거 그려줘", "이 URL 가져와줘"라고 요청을 보내는 구조다.
- 한 탭의 메모리 = 그 탭의 렌더러 프로세스 메모리 + GPU 프로세스 안의 그 탭 몫(텍스처 등) + 네트워크 버퍼 일부
- 탭이 닫히면 그 탭의 GPU 자원은 해제되지만 GPU 프로세스 자체는 계속 살아 있다.
- "탭 = 렌더러 1개"는 기본 원칙이다. 실제로는 사이트 단위(Site Isolation)라서, 한 탭 안의 다른 사이트 iframe은 별도 렌더러로 갈 수 있고, 같은 사이트의 탭들은 렌더러를 공유할 수 있다. 프로세스가 많아지면 일부 탭이 렌더러를 공유한다.

#### 2-3. 프로세스의 메모리 영역: 각 영역에 뭐가 들어가나

##### 전체 배치 (낮은 주소 → 높은 주소)

```text
낮은 주소
┌─────────────────────────┐
│ 코드(text)              │  기계어 명령어, 읽기·실행 전용
├─────────────────────────┤
│ 데이터 (.data)          │  초기값 있는 전역·정적 변수
├─────────────────────────┤
│ BSS (.bss)              │  초기값 없는(0으로 채워지는) 전역·정적 변수
├─────────────────────────┤
│ 힙 ↓ (위로 자람)        │  malloc/new로 동적 할당
│          ...            │
│ mmap 영역               │  큰 덩어리, 파일 매핑, 공유 메모리, 스레드 스택 등
│          ...            │
│ 스택 ↑ (아래로 자람)    │  함수 호출 프레임
└─────────────────────────┘
높은 주소
```

(실제 배치는 OS와 ASLR 같은 보안 기능 때문에 매번 달라진다. 개념도이다.)

##### 영역별 내용

| 영역          | 개수                            | 들어가는 것                                                                              | 크기                                               | 수명                                 |
| ------------- | ------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------ |
| 코드(text)    | 프로세스당 1개                  | 컴파일된 함수들의 기계어 명령어, 상수 문자열 리터럴(보통 읽기 전용 영역). 읽기·실행 전용 | 실행 파일 크기로 고정                              | 프로세스 시작~종료                   |
| 데이터(.data) | 프로세스당 1개                  | `int count = 5;` 같은 초기값 있는 전역·static 변수                                       | 고정                                               | 프로세스 전체                        |
| BSS(.bss)     | 프로세스당 1개                  | `int total;` 같은 초기값 없는 전역·static 변수 (0으로 초기화)                            | 고정                                               | 프로세스 전체                        |
| 힙            | 프로세스당 1개                  | `malloc`/`new`로 요청한 객체, 배열, 버퍼                                                 | 런타임에 증감                                      | 해제할 때까지 (직접 `free`/`delete`) |
| mmap          | 프로세스당 1개 (안에 여러 매핑) | 큰 할당, 파일 매핑, 공유 메모리, 스레드 스택, V8 힙·JIT 코드 같은 큰 영역                | 페이지(보통 4KB) 단위                              | `munmap`할 때까지                    |
| 스택          | **스레드당 1개**                | 함수 호출 프레임                                                                         | 스레드 생성 시 정해진 한도(보통 수 MB) 안에서 증감 | 함수 종료 시 자동 해제               |

- 여기서 "힙"은 OS 프로세스의 힙이며, V8의 JS 힙과 다른 개념이다.
- 정확한 표현은 "프로세스가 코드·데이터·힙을 하나씩, 스택은 스레드 수만큼" 가진다.
- 코드 영역은 논리적으로는 프로세스마다 독립이지만, 같은 실행 파일로 띄운 여러 프로세스는 OS가 **물리 메모리의 코드 페이지를 공유**해 중복을 줄이는 것이 일반적이다. (읽기 전용이라 가능, 세부 동작은 OS마다 다름)

##### 코드(text) 영역이란

- "코드"는 소스 코드가 아니라 **컴파일된 기계어 명령어**다. 예를 들어 `add` 함수가 컴파일된 결과 명령어들이 여기 있고, CPU는 이 영역의 명령어를 하나씩 읽어 실행한다.
- 실행 중에 바뀌지 않으므로 읽기·실행 전용이며, 그래서 여러 프로세스가 물리 메모리를 공유할 수 있다.
- JIT 컴파일러(V8)는 실행 중에 기계어를 새로 만들어야 하므로, 이 text 영역이 아니라 **mmap으로 받은 실행 권한 메모리**에 둔다.

##### 스택에 쌓이는 것: 호출 프레임

함수를 호출할 때마다 **스택 프레임** 하나가 쌓이고, 함수가 끝나면 그 프레임이 사라진다. 프레임 안에는 다음이 들어간다.

- 반환 주소: 함수가 끝나면 돌아갈 위치
- 인자: 호출 시 넘긴 값 (일부는 레지스터로 전달)
- 지역 변수: 함수 안에서 선언한 변수
- 저장된 레지스터 값: 호출 전 상태 복원용 백업
- 이전 프레임을 가리키는 포인터

```c
int add(int a, int b) {
    int sum = a + b;     // sum: add의 스택 프레임 안
    return sum;
}

int main() {
    int x = 10;                         // x: main의 스택 프레임
    int *p = malloc(sizeof(int) * 3);   // p(포인터)는 스택, 가리키는 12바이트는 힙
    p[0] = add(x, 5);                   // add 호출 → 새 프레임이 스택 위에 쌓임
    free(p);                            // 힙은 직접 해제해야 함
    return 0;
}
```

```text
add 호출 중의 스택

  ┌──────────────────────┐ ← 먼저 쌓임
  │ main 프레임           │
  │   x = 10             │
  │   p = 0x7f...(힙 주소)│  ← p 자체는 스택, 가리키는 곳은 힙
  ├──────────────────────┤
  │ add 프레임            │
  │   반환 주소 (main으로)│
  │   a = 10, b = 5      │
  │   sum = 15            │
  └──────────────────────┘ ← 가장 최근. add가 끝나면 이 프레임만 사라짐
```

- add가 `return`하면 프레임이 버려지고 main으로 돌아온다. 스택은 해제를 신경 쓸 필요가 없는 대신, 함수가 끝나면 지역 변수도 사라진다.

##### 스택 vs 힙

|           | 스택                                             | 힙                                                          |
| --------- | ------------------------------------------------ | ----------------------------------------------------------- |
| 할당 방식 | 함수 호출 시 자동 (포인터 한 칸 이동)            | `malloc`/`new`로 직접 요청                                  |
| 해제 방식 | 함수 종료 시 자동                                | 직접 해제 (JS는 GC가 대신)                                  |
| 속도      | 매우 빠름                                        | 상대적으로 느림 (빈 공간 탐색 필요)                         |
| 크기      | 작음, 한도 초과 시 stack overflow                | 큼 (메모리 허용 범위까지)                                   |
| 저장 대상 | 크기가 컴파일 시점에 정해진 지역 변수, 호출 정보 | 크기가 런타임에 정해지거나 함수가 끝나도 살아야 하는 데이터 |
| 접근      | 호출 순서대로 (LIFO)                             | 포인터로 아무 순서나                                        |

- 핵심: **함수가 끝나도 살아 있어야 하는 데이터는 스택에 둘 수 없다.** 프레임이 사라지기 때문이다. 그래서 그런 데이터는 힙에 두고, 스택에는 그걸 가리키는 포인터만 둔다. JS에서 객체가 V8 힙에 있고 변수(참조)가 스택에 있는 것도 같은 원리다.

#### 2-4. 스레드

| 영역            | 프로세스당 하나 (스레드 공유) | 스레드마다 하나 |
| --------------- | ----------------------------- | --------------- |
| 코드            | O                             |                 |
| 데이터          | O                             |                 |
| 힙 / mmap       | O                             |                 |
| 스택            |                               | O               |
| CPU 레지스터 값 |                               | O               |

- 스택에는 호출 프레임이 쌓인다. 스레드마다 호출 흐름이 달라서 OS가 전용 스택(보통 수 MB)을 할당한다.
- 힙은 공유되므로 한 스레드가 만든 객체를 다른 스레드가 접근할 수 있고, 동시 접근 시 락 같은 동기화가 필요하다.

```text
렌더러 프로세스
├─ 코드 / 데이터 / 힙·mmap 영역   ← 모든 스레드 공유
├─ 스레드 A (메인 스레드)  → 자기 스택 A
├─ 스레드 B (Worker)       → 자기 스택 B
└─ 스레드 C (컴포지터 등)  → 자기 스택 C
```

### 3. 엔진 층위: V8

V8은 렌더러 프로세스 안에서 동작하며, OS에서 큰 덩어리(주로 mmap)를 받아 자기 방식으로 관리한다. 2-3의 "스택 vs 힙" 원리를 JS 수준에서 그대로 적용한 구조다.

#### 3-1. 영역별 정리

| 구분      | 메모리 출처                             | 쓰는 주체                   | 관리                                     | 내용                                                                                 |
| --------- | --------------------------------------- | --------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------ |
| JS 힙     | mmap                                    | V8                          | V8 (GC)                                  | JS 객체, 배열, 함수 객체, 클로저 환경(Context), 문자열, 바이트코드. Young/Old로 구분 |
| 코드 영역 | mmap (실행 권한 페이지)                 | V8                          | V8                                       | JIT 컴파일된 기계어                                                                  |
| 호출 스택 | 스레드 스택 (OS가 할당, 보통 mmap 기반) | 스레드 (V8은 프레임만 쌓음) | OS/스레드, 함수 종료 시 프레임 자동 제거 | 반환 주소, 인자, 지역 변수 (C++ 프레임과 JS 프레임이 섞임)                           |

#### 3-2. 전체 그림

```text
렌더러 프로세스 (OS가 준 가상 주소 공간)
├─ 코드(text) / 데이터 / 힙(malloc) 영역   ← Chrome(Blink 등) C++ 코드가 사용
│
├─ mmap 영역
│   ├─ V8 JS 힙          ← V8이 분할·관리 (GC)
│   ├─ V8 코드 영역       ← V8이 관리 (JIT 기계어, 실행 권한)
│   └─ 스레드 스택들      ← OS가 스레드에 할당 (보통 mmap 기반), V8 관리 대상 아님
│
└─ 메인 스레드
    └─ 자기 스택: Chrome C++ 프레임 → V8 C++ 프레임 → JS 함수 프레임
```

#### 3-3. 핵심 포인트

- **V8의 위치**: 탭(사이트)의 렌더러 프로세스 안에서 동작하며, JS는 메인 스레드에서 실행된다.
- **힙과 코드**: V8이 mmap으로 받은 큰 덩어리를 자기 방식으로 쪼개 쓴다.
- **스택**: V8이 나누거나 관리하지 않는다. 스레드 스택은 물리적으로는 프로세스 가상 주소 공간 안(보통 mmap)에 있지만, **누가 쓰고 관리하느냐**가 V8의 힙·코드와 다르다. 메인 스레드의 스택은 프로세스 시작 시 OS가 별도로 세팅하고, 그 외 스레드의 스택은 mmap으로 확보되는 경우가 많다.
- **네이티브 스택**: OS가 그 스레드에 준 일반 스택(C/C++이 쓰는 스택). V8은 새 스택을 만들지 않고 이 위에 JS 프레임을 쌓으므로 C++ 프레임과 JS 프레임이 같은 스택에 섞여 있다.
- JS 프레임에도 반환 주소, 인자, 지역 변수가 들어간다. 최적화된 코드(TurboFan)에서는 지역 변수가 스택 대신 CPU 레지스터에 있기도 하다.
- **Web Worker**: 별도 스레드라서 자기 스택과 독립된 V8 힙(Isolate)을 가진다. 메인 스레드와 JS 객체를 공유하지 않아 `postMessage`로 복사해 전달한다. (같은 프로세스이므로 OS 층위의 코드·힙 영역은 같은 주소 공간을 쓴다.)

```text
메인 스레드의 스택
  ┌──────────────────────┐ ← 먼저 쌓인 것
  │ Chrome C++ 프레임     │ (이벤트 루프 등)
  ├──────────────────────┤
  │ V8 C++ 프레임         │ (JS 실행 시작 코드)
  ├──────────────────────┤
  │ JS 함수 foo 프레임    │ ← 반환 주소, 인자, 지역 변수
  ├──────────────────────┤
  │ JS 함수 bar 프레임    │
  └──────────────────────┘ ← 가장 최근
```

#### 3-4. 헷갈리기 쉬운 점

- "JS 힙 / 코드 / 스택"으로 묶어 외우기 쉽지만 **주체가 다르다.** 힙·코드는 V8, 스택은 OS가 스레드에 준 것이다.
- **바이트코드**는 코드 영역이 아니라 JS 힙에 있다. 코드 영역에는 JIT이 만든 **기계어**만 들어간다.
- 지역 변수는 기본적으로 스택이지만, 최적화된 코드에서는 CPU 레지스터에 있기도 하고, 클로저에 잡히면 힙(Context)으로 간다.
- V8의 "JS 힙"은 OS 프로세스의 힙(malloc 영역)과 다른 개념이다.

### 4. 언어 층위: JS 개념의 저장 위치

(기본 모델이며, 엔진 최적화에 따라 달라질 수 있음)

| JS 개념                     | 일반적인 저장 위치          | 예외·최적화                                             |
| --------------------------- | --------------------------- | ------------------------------------------------------- |
| 객체, 배열, 함수 객체       | V8 힙                       | 탈출 분석으로 제거되면 메모리에 없을 수도 있음          |
| 지역 변수 (원시값)          | 호출 스택                   | 레지스터에 있거나, 클로저에 잡히면 힙(Context)으로 이동 |
| 객체를 가리키는 변수 (참조) | 호출 스택                   | 위와 동일                                               |
| 작은 정수                   | 값 자체가 슬롯에 저장 (Smi) | 큰 수·소수는 힙에 박싱(HeapNumber)                      |
| 문자열                      | V8 힙                       | 상수 문자열은 공유·인터닝 가능                          |
| 클로저가 잡은 변수          | V8 힙 (Context)             | 잡히지 않으면 스택                                      |
| 바이트코드                  | V8 힙                       |                                                         |
| JIT 기계어                  | V8 코드 영역                |                                                         |

```jsx
function foo() {
  const n = 1; // 스택/레지스터 (또는 Smi)
  const user = { name: "건우" }; // user(참조)는 스택, 객체는 V8 힙
  return () => user; // user가 클로저에 잡힘 → Context 객체가 V8 힙으로
}
```

- 클로저가 힙으로 가는 이유는 2-3의 핵심과 같다. `foo`가 끝나면 프레임이 사라지지만 `user`는 반환된 함수가 계속 써야 하므로, 스택에 둘 수 없고 힙(Context)에 둔다.

### 5. 브라우저 구성요소별 메모리 위치

JS 외의 자원은 V8이 관리하지 않고, 같은 렌더러 프로세스의 네이티브 메모리나 다른 프로세스에 있다.

| 항목                   | 프로세스                                 | 위치                                                 |
| ---------------------- | ---------------------------------------- | ---------------------------------------------------- |
| JS 객체·클로저         | 렌더러                                   | V8 힙                                                |
| DOM / CSSOM            | 렌더러                                   | Blink 네이티브 메모리 (Oilpan GC 힙, PartitionAlloc) |
| 레이아웃·페인트 데이터 | 렌더러                                   | 네이티브 힙                                          |
| 디코딩된 이미지        | 렌더러 (일부 GPU 프로세스로 전달)        | 네이티브 힙, 공유 메모리                             |
| Canvas·WebGL 텍스처    | GPU 프로세스 (공유)                      | VRAM 또는 공유 시스템 메모리                         |
| 네트워크 버퍼          | 네트워크 서비스 프로세스 (공유) + 렌더러 | 네이티브 힙                                          |
| Web Worker             | 렌더러 (별도 스레드)                     | 자기 스택 + 독립된 V8 힙(Isolate)                    |

- JS에서 얻은 DOM 객체는 JS 래퍼 객체(V8 힙) → C++ DOM 객체(Blink 메모리)로 연결된다.
- 그래서 JS 참조 하나가 네이티브 메모리까지 붙잡을 수 있고, 이것이 detached DOM 누수의 원인이다.
- 따라서 JS 힙은 작아도 탭 전체 메모리는 클 수 있다.

JS 값의 저장 방식, 도달 가능성, V8의 GC, 클로저와 JavaScript 메모리 누수는 [JavaScript 메모리 구조와 관리](/blog/javascript-memory-management-v8)에서 별도로 설명한다.

### 6. 메모리 관리: 브라우저 차원

- **프로세스 격리**
  - 렌더러가 탭(사이트) 단위로 분리되어, 탭끼리 메모리를 직접 공유하지 않는다.
  - 프로세스가 많아지면 일부 탭은 렌더러를 공유할 수 있다.
- **물리 메모리는 공유**
  - 가상 메모리는 분리돼도 실제 RAM은 한정되어 있어, 모든 프로세스(렌더러, GPU, 네트워크 등)가 같은 물리 메모리를 두고 경쟁한다.
- **백그라운드 탭 폐기(discard)**
  - 메모리가 부족하면 보이지 않는 오래된 탭을 폐기해 메모리를 확보한다.
  - 다시 클릭하면 페이지를 처음부터 재로드한다.
- **메모리 압박 대응**: OS의 메모리 부족 신호를 받으면 캐시를 비우는 등 사용량을 줄인다.

### 7. 확인 방법

- Task Manager (Shift+Esc): 브라우저, GPU, 탭별, 확장 프로그램 프로세스를 따로 확인 (DevTools가 아닌 Chrome 기능). OS 작업 관리자에서도 chrome 프로세스가 여러 개 보인다.
- DevTools Memory 탭: Heap Snapshot으로 남은 객체, detached DOM 확인
- DevTools Performance 탭: 시간에 따른 메모리 증가 추이
- JS 힙과 브라우저 전체 메모리를 구분해 확인하고, JS 메모리의 GC·누수 분석은 [JavaScript 메모리 구조와 관리](/blog/javascript-memory-management-v8)의 진단 방법을 따른다.

## 참고

- Chrome(Blink/V8) 기준 구현 세부사항이며, Firefox·Safari는 구조와 이름이 다르다. (Firefox도 멀티 프로세스지만 구성이 다르다.)
- GPU·네트워크 서비스가 별도 프로세스인 것은 플랫폼과 버전에 따라 다를 수 있다. (예: 네트워크 서비스를 브라우저 프로세스 안에서 실행)
- 메모리 배치 그림(주소 방향, 영역 순서)은 개념도이며, 실제로는 OS·아키텍처·ASLR에 따라 달라진다.
- "원시값은 스택, 객체는 힙"은 개념 이해용 기본 모델이고, 실제 엔진은 최적화로 달라질 수 있다.
- Oilpan의 관리 범위, 바이트코드의 V8 힙 위치, 렌더러의 스레드 구성은 버전에 따라 달라질 수 있다.
- 물리 메모리에서의 코드 페이지 공유 등 OS 수준 동작은 운영체제마다 세부적으로 다르다.
