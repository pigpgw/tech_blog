## 핵심

> 브라우저는 하나의 프로세스가 모든 메모리를 관리하지 않습니다. 브라우저·렌더러·GPU·네트워크 프로세스가 역할을 나누어 페이지, JavaScript, 화면, 네트워크를 처리합니다. 페이지를 닫으면 관련 자원이 정리되지만, SPA에서는 페이지가 계속 실행되므로 컴포넌트가 제거될 때 이벤트·타이머·WebSocket·Worker를 직접 정리해야 합니다.

## 요약

브라우저 메모리는 JavaScript만을 의미하지 않습니다. JavaScript 객체, DOM·CSSOM, 이미지, Canvas, Web Worker, WebSocket, GPU 리소스가 함께 메모리를 사용합니다.

Chrome은 여러 프로세스로 역할을 나눕니다. 브라우저 프로세스는 탭과 권한을 관리하고, 렌더러 프로세스는 HTML·CSS·JavaScript를 처리합니다. GPU 프로세스는 화면과 그래픽을 처리하고, 네트워크 서비스는 요청과 연결을 처리합니다. 이 구조는 한 기능에 문제가 생겨도 다른 기능에 영향을 줄이고, 자원을 역할별로 관리하기 위한 것입니다.

페이지를 닫으면 페이지와 연결된 자원이 함께 정리됩니다. 그러나 SPA는 페이지를 유지한 채 화면만 바꾸므로, 제거된 컴포넌트의 이벤트 리스너·타이머·WebSocket·Worker가 남지 않도록 개발자가 정리해야 합니다. 메모리 누수는 화면에서 사라진 자원이 계속 남아 메모리를 사용하는 현상입니다.

> 핵심은 메모리 관리 주체가 하나가 아니라는 점입니다. 운영체제는 프로세스와 스레드의 메모리 공간을 관리하고, 렌더러는 페이지 자원을, V8은 JavaScript 객체를, GPU와 네트워크 서비스는 각자의 자원을 관리합니다. 개발자는 이벤트·타이머·연결처럼 직접 만든 사용 관계를 정리합니다.

## Deep Dive

### 1. 브라우저는 여러 프로세스로 동작한다

```text
브라우저 프로세스  : 탭 UI, 권한, 프로세스 관리
렌더러 프로세스    : HTML, CSS, DOM, JavaScript 실행
GPU 프로세스        : Canvas, WebGL, 화면 합성
네트워크 서비스     : 요청, 응답, 연결, 네트워크 버퍼
```

프로그램이 실행되면 운영체제는 프로세스마다 독립된 가상 메모리 공간을 제공합니다. Chrome은 이 공간을 브라우저, 렌더러, GPU, 네트워크 같은 프로세스로 나누어 사용합니다.

렌더러 프로세스 안에서 JavaScript는 V8 엔진으로 실행됩니다. 다만 DOM·이미지·Canvas·GPU·네트워크까지 모두 V8이 관리하는 것은 아닙니다. 각 자원은 해당 브라우저 구성요소가 관리합니다.

> 탭과 렌더러의 관계는 항상 1:1은 아닙니다. 사이트 격리 정책과 iframe 구성에 따라 하나의 탭에 여러 렌더러가 사용되거나, 여러 탭이 렌더러를 공유할 수 있습니다.

### 2. 브라우저 메모리에 포함되는 자원

| 자원         | 주로 처리하는 곳       | 메모리에 보관되는 것                   |
| ------------ | ---------------------- | -------------------------------------- |
| JavaScript   | 렌더러·V8              | 객체, 배열, 함수, 실행 정보            |
| DOM·CSSOM    | 렌더러                 | 문서 구조, 스타일, 레이아웃 정보       |
| 이미지       | 렌더러·GPU             | 이미지 객체와 디코딩된 픽셀 데이터     |
| Canvas·WebGL | 렌더러·GPU             | 캔버스 픽셀, 텍스처, 그래픽 버퍼       |
| Web Worker   | 렌더러의 별도 스레드   | Worker의 실행 정보와 JavaScript 데이터 |
| WebSocket    | 네트워크 서비스·렌더러 | 연결 상태, 송수신 버퍼, 이벤트 콜백    |
| GPU 리소스   | GPU 프로세스           | 텍스처, 버퍼, 렌더링 결과              |

Chrome 작업 관리자에서 `JavaScript memory`가 작게 보여도 탭 전체 메모리가 작은 것은 아닙니다. 사진을 화면에 띄우거나 Canvas·WebGL을 사용하면 실제 이미지와 그래픽 데이터가 JavaScript 메모리와 다른 곳에 저장될 수 있기 때문입니다. 따라서 메모리 문제를 확인할 때는 JavaScript memory만 보지 말고 Chrome 작업 관리자의 탭 전체 메모리도 함께 확인해야 합니다.

### 3. 메모리의 할당과 회수

브라우저는 페이지를 실행할 때 필요한 메모리를 운영체제와 각 구성요소로부터 확보합니다. 페이지가 사용하는 동안 DOM·이미지·그래픽·네트워크 데이터를 보관하고, 더 이상 필요하지 않은 자원을 정리합니다.

- JavaScript 객체: V8이 객체 사이의 참조를 추적하고, GC 루트에서 접근할 수 없는 객체를 가비지 컬렉터로 회수합니다.
- DOM: 렌더러가 DOM을 관리하며, 문서에서 제거되고 JavaScript와 다른 DOM 객체의 참조도 사라지면 회수 대상으로 만듭니다.
- 이미지: 이미지 디코더와 브라우저 캐시가 관리하며, 참조가 사라지거나 메모리 압박이 생기면 디코딩 데이터를 버릴 수 있습니다.
- Canvas·GPU: 브라우저와 GPU 프로세스가 그래픽 리소스를 관리합니다. WebGL 텍스처·버퍼처럼 개발자가 직접 만든 리소스는 API로 삭제해야 합니다.
- WebSocket·Worker: 네트워크 서비스와 렌더러가 실행을 관리하지만, 연결을 닫거나 Worker를 종료해야 관련 자원이 해제됩니다.

#### 누가 관리하는가

| 관리 주체       | 관리하는 대상                              | 실제로 처리하는 방식                                                                |
| --------------- | ------------------------------------------ | ----------------------------------------------------------------------------------- |
| 운영체제(OS)    | 프로세스와 스레드의 메모리 공간            | 프로세스별 주소 공간을 분리하고 메모리 페이지와 스레드 스택을 제공합니다.           |
| 브라우저·렌더러 | DOM·CSSOM·레이아웃·이미지                  | 브라우저 내부 객체와 할당기를 관리하고 참조와 캐시 상태에 따라 정리합니다.          |
| V8 엔진         | JavaScript 객체·배열·함수                  | GC 루트에서 참조를 따라가 도달할 수 없는 객체를 가비지 컬렉터가 회수합니다.         |
| 네트워크 서비스 | 요청·응답·WebSocket 버퍼                   | 소켓과 버퍼의 수명을 관리하고 요청이 끝나거나 연결이 닫히면 자원을 반환합니다.      |
| GPU 프로세스    | Canvas·WebGL 텍스처·그래픽 버퍼            | 그래픽 리소스를 생성·사용·해제하며, API 호출이나 컨텍스트 종료로 삭제합니다.        |
| 개발자          | 이벤트·타이머·WebSocket·Worker의 사용 관계 | 컴포넌트 수명에 맞춰 리스너 제거, 타이머 해제, 연결 종료, Worker 종료를 수행합니다. |

즉, 운영체제는 메모리를 담을 공간과 보호 기능을 제공하고, 브라우저 구성요소는 그 공간 안에서 각 자원의 생성·참조·캐시·GC·명시적 해제를 관리합니다. 애플리케이션이 객체나 콜백을 계속 참조하면 브라우저가 그 참조를 임의로 끊을 수 없으므로 개발자의 cleanup이 필요합니다.

### 4. 페이지 종료와 SPA의 차이

페이지를 닫거나 이동하면 해당 페이지의 실행 환경이 종료되면서 대부분의 자원이 함께 정리됩니다.

반면 SPA는 페이지와 렌더러가 계속 살아 있는 상태에서 컴포넌트만 제거합니다. 따라서 컴포넌트가 사라질 때 다음 작업을 직접 해야 합니다.

- 이벤트 리스너 제거
- 타이머 해제
- WebSocket 연결 종료
- Worker 종료
- Observer 해제
- Canvas·WebGL·Blob URL 등 별도 자원 정리

### 5. 브라우저 메모리 누수

브라우저 메모리 누수는 화면에서 더 이상 사용하지 않는 자원이 계속 남아 있는 현상입니다.

- 제거한 DOM을 JavaScript 변수나 배열이 계속 참조하는 경우
- 이벤트 리스너와 타이머를 제거하지 않은 경우
- WebSocket과 Worker를 종료하지 않은 경우
- 배열·Map·캐시가 계속 커지는 경우
- 이미지·Canvas·WebGL 리소스를 사용 후에도 유지하는 경우

JS 힙뿐 아니라 DOM, 이미지, GPU 메모리도 함께 확인해야 합니다.

### 6. 캐시와 백그라운드 탭 관리

브라우저는 이미지·스크립트·폰트처럼 다시 사용할 데이터를 캐시에 보관합니다. 저장 공간이나 메모리가 부족하면 오래 사용하지 않은 캐시를 제거합니다.

메모리 압박이 심하면 백그라운드 탭의 실행을 제한하거나 탭을 폐기할 수 있습니다. 폐기된 탭을 다시 열면 페이지가 새로 로드될 수 있습니다. 이 과정은 JavaScript 코드가 직접 제어하는 것이 아니라 브라우저와 운영체제가 결정합니다.

### 7. Chrome DevTools로 확인하기

#### Chrome 작업 관리자

`Shift + Esc`로 Chrome 작업 관리자를 열면 탭·GPU·브라우저 프로세스의 전체 메모리를 확인할 수 있습니다. `JavaScript memory` 항목을 추가하면 JavaScript 힙과 탭 전체 메모리를 비교할 수 있습니다.

#### Heap Snapshot

DevTools → Memory → Heap snapshot에서 특정 시점의 JavaScript 객체를 확인합니다.

1. 기준 스냅샷을 찍습니다.
2. 같은 동작을 여러 번 반복합니다.
3. 두 번째 스냅샷을 찍고 Comparison으로 비교합니다.
4. `Detached` 객체와 Retainers에서 계속 남아 있는 이유를 확인합니다.

#### Performance

Performance 탭에서 Memory를 선택하면 시간에 따른 JavaScript 힙, DOM 개수, 이벤트 리스너 수의 변화를 확인할 수 있습니다. GC 이후에도 기준선이 계속 올라가면 누수를 의심합니다.

### 8. 브라우저 메모리 관리 면접 질문

#### 브라우저는 메모리를 어떻게 관리하나요?

브라우저 메모리는 한 주체가 모두 관리하지 않습니다. 운영체제는 프로세스에 메모리 공간을 제공하고, 렌더러는 DOM과 페이지 자원을, V8은 참조를 추적하는 GC로 JavaScript 객체를, GPU와 네트워크 서비스는 그래픽·연결 자원을 관리합니다. SPA에서는 페이지가 계속 유지되므로 컴포넌트 제거 시 이벤트·타이머·연결·Worker를 개발자가 직접 정리해야 합니다.

#### JavaScript 힙이 작아도 탭 메모리가 클 수 있는 이유는 무엇인가요?

DOM·이미지·Canvas·GPU·네트워크 버퍼가 JavaScript 힙과 별도로 메모리를 사용할 수 있기 때문입니다. 그래서 JavaScript 힙뿐 아니라 Chrome 작업 관리자의 전체 메모리도 함께 확인해야 합니다.

#### 페이지 이동과 SPA 컴포넌트 제거는 어떻게 다른가요?

페이지 이동은 페이지 실행 환경이 종료되면서 관련 자원이 정리됩니다. SPA는 페이지가 유지된 채 컴포넌트만 제거되므로 이벤트 리스너·타이머·WebSocket·Worker를 직접 정리해야 합니다.
