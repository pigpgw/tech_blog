## 핵심

> JavaScript에서는 가비지 컬렉터가 더 이상 사용되지 않는 객체를 자동으로 회수합니다. 개발자는 메모리를 직접 해제하는 대신, 전역 변수·캐시·클로저처럼 객체를 계속 참조하는 코드를 정리해야 합니다.

## 요약

JavaScript는 값을 만들고 사용하는 동안 필요한 메모리를 자동으로 할당합니다. 이후 가비지 컬렉터가 다른 코드에서 더 이상 접근할 수 없는 객체를 찾아 메모리를 회수합니다. 객체가 아직 변수나 다른 객체에서 참조되고 있으면 회수되지 않습니다.

원시값은 값 자체가 복사되고, 객체·배열·함수는 객체를 가리키는 참조가 복사됩니다. 따라서 변수에 `null`을 대입해도 객체가 즉시 삭제되는 것은 아니며, 해당 객체로 이어지는 참조가 모두 끊겨야 회수 대상이 됩니다.

메모리 누수는 사용하지 않는 객체가 계속 참조되는 현상입니다. 전역 변수, 계속 커지는 배열·Map·캐시, 큰 데이터를 붙잡은 클로저, 정리하지 않은 이벤트·타이머·WebSocket 등이 대표적인 원인입니다. React에서는 컴포넌트가 제거될 때 이런 작업을 cleanup해야 합니다.

## Deep Dive

### 1. JavaScript 메모리 생명주기

JavaScript의 메모리 사용은 크게 세 단계로 볼 수 있습니다.

1. **할당**: 객체·배열·함수·문자열 등을 만들 때 엔진이 메모리를 확보합니다.
2. **사용**: 프로그램이 값을 읽고 변경합니다.
3. **회수**: 더 이상 접근할 수 없는 객체를 가비지 컬렉터가 정리합니다.

```js
let user = { name: "건우" }; // 객체 생성
console.log(user.name); // 객체 사용
user = null; // 참조를 끊음. 즉시 삭제되는 것은 아님
```

개발자는 `free()`처럼 객체를 직접 해제하지 않습니다. 참조를 정리해 가비지 컬렉터가 회수할 수 있는 상태를 만드는 것이 개발자가 하는 일입니다.

### 2. 코드·변수·데이터의 메모리 구조

JavaScript 표준은 값이 실제 메모리의 어느 위치에 저장되는지 정하지 않습니다. 표준은 코드가 실행되는 상태를 **실행 컨텍스트**라는 개념으로 설명합니다.

> 실행 컨텍스트: JavaScript 코드가 실행될 때 필요한 정보를 묶어 관리하는 단위입니다. 어떤 함수가 실행 중인지, 식별자를 어디에서 찾는지, 코드가 어디까지 실행됐는지 등을 포함합니다.

함수가 호출되면 새로운 실행 컨텍스트가 실행 컨텍스트 스택에 올라가고, 실행이 끝나면 내려옵니다. 이 개념은 실행 과정을 설명하기 위한 표준 모델이며, 실제 메모리의 한 영역과 일치하는 것은 아닙니다.

V8에서는 함수 호출에 필요한 정보가 호출 스택의 프레임으로 관리될 수 있습니다. 객체·배열·함수 객체처럼 수명과 크기가 달라질 수 있는 값은 보통 V8 힙에서 관리됩니다. 다만 최적화에 따라 값이 CPU 레지스터에 있거나, 클로저를 위한 환경에 보관될 수도 있습니다.

> “지역 변수는 항상 스택에 있고 객체는 항상 힙에 있다”는 표현은 이해를 위한 기본 모델입니다. 실제 저장 위치는 JavaScript 표준이 아니라 엔진 구현과 최적화 결과에 따라 달라집니다.

### 3. 스택과 힙의 차이

| 구분             | 스택                                    | 힙                                     |
| ---------------- | --------------------------------------- | -------------------------------------- |
| 주로 관리하는 것 | 함수 호출 정보와 실행 흐름              | 객체처럼 수명과 크기가 달라지는 데이터 |
| 동작 방식        | 함수 호출 순서대로 쌓이고 끝나면 사라짐 | 참조가 남아 있는 동안 유지됨           |
| 관리 방식        | 함수 실행 흐름에 따라 자동 관리         | 가비지 컬렉터가 사용 가능 여부를 판단  |

스택과 힙은 이해를 위한 기본 모델입니다. 실제 JavaScript 엔진은 성능을 위해 값을 레지스터에 두거나, 필요 없는 객체를 최적화로 제거할 수 있습니다.

### 4. 원시값과 객체의 참조

원시값은 하나의 값입니다. 다른 변수에 복사하면 값이 복사됩니다.

```js
let first = 10;
let second = first;
second = 20;

console.log(first); // 10
```

객체는 변수에 객체 자체가 아니라 객체를 가리키는 참조가 저장됩니다. 다른 변수에 대입하면 같은 객체를 가리키는 참조가 복사됩니다.

```js
const firstUser = { name: "건우" };
const secondUser = firstUser;

secondUser.name = "민수";
console.log(firstUser.name); // 민수
```

### 5. 가비지 컬렉션과 도달 가능성

가비지 컬렉터는 객체가 “지금 사용 중인지”를 직접 묻는 것이 아니라, 프로그램의 시작점에서 그 객체까지 찾아갈 수 있는지를 확인합니다.

> GC 루트: 가비지 컬렉터가 객체를 추적하기 시작하는 지점입니다. 전역 객체나 현재 실행 중인 코드가 참조하는 값 등이 여기에 포함될 수 있습니다.

```js
let first = { name: "A" };
let second = { friend: first };

first = null; // second.friend가 first를 참조하므로 아직 회수되지 않음
second = null; // 이제 두 객체 모두 GC 대상이 될 수 있음
```

서로를 가리키는 순환 참조도 GC 루트에서 접근할 수 없다면 회수할 수 있습니다. 가비지 컬렉터는 도달할 수 있는 객체를 남기고, 도달할 수 없는 객체를 정리합니다.

### 6. 참조를 끊으면 바로 해제되나요?

아닙니다. 참조를 끊으면 가비지 컬렉터가 해당 객체를 회수할 수 있는 상태가 될 뿐입니다. 실제 회수 시점은 엔진이 결정합니다.

```js
let data = { items: new Array(1000).fill("data") };
data = null; // 회수 가능 상태가 됨. 즉시 메모리 해제는 아님
```

다른 변수나 배열이 같은 객체를 참조하고 있다면 `null`을 대입해도 객체는 살아 있습니다.

### 7. 클로저가 메모리에 영향을 주는 이유

클로저는 함수가 선언된 바깥 환경의 변수를 계속 사용할 수 있는 함수입니다. 바깥 함수의 실행이 끝난 뒤에도 반환된 함수가 변수를 사용해야 하므로, 엔진은 해당 변수를 계속 보관할 수 있습니다.

```js
function createCounter() {
  let count = 0;
  return () => ++count;
}

const counter = createCounter();
console.log(counter()); // 1
```

`createCounter`의 실행이 끝난 뒤에도 `counter`가 `count`를 사용하므로 `count`는 회수되지 않습니다. 클로저가 큰 객체까지 참조하면 필요 이상으로 큰 데이터가 오래 남을 수 있습니다.

### 8. JavaScript 메모리 누수

JavaScript 메모리 누수는 더 이상 사용하지 않는 객체가 계속 참조되는 현상입니다.

| 원인                 | 설명                                   | 해결 방법                      |
| -------------------- | -------------------------------------- | ------------------------------ |
| 전역 변수            | 프로그램이 끝날 때까지 참조가 유지됨   | 필요한 범위 안에서 변수 선언   |
| 커지는 배열·Map·캐시 | 데이터를 추가하기만 하고 삭제하지 않음 | 크기 제한과 오래된 데이터 삭제 |
| 클로저               | 함수가 큰 데이터를 계속 참조함         | 필요한 값만 캡처               |
| 이벤트·타이머·연결   | 콜백이 객체를 계속 참조함              | 사용이 끝나면 제거·종료        |

### 9. React에서 리소스 정리

React 컴포넌트가 사라질 때도 JavaScript 참조가 남아 있으면 관련 객체가 회수되지 않을 수 있습니다. `useEffect`의 cleanup 함수에서 등록한 작업을 정리합니다.

```jsx
useEffect(() => {
  const onResize = () => {};
  window.addEventListener("resize", onResize);

  const timerId = setInterval(tick, 1000);
  const socket = new WebSocket(url);

  return () => {
    window.removeEventListener("resize", onResize);
    clearInterval(timerId);
    socket.close();
  };
}, []);
```

이벤트 리스너, 타이머, WebSocket처럼 컴포넌트보다 오래 살아 있을 수 있는 작업은 생성한 곳에서 정리하는 것이 좋습니다.

## 면접 질문

### JavaScript의 메모리 관리 방식은 어떻게 되나요?

JavaScript에서는 가비지 컬렉터가 더 이상 접근할 수 없는 객체를 자동으로 회수합니다. 개발자는 메모리를 직접 해제하지 않고, 전역 변수·캐시·클로저·이벤트·타이머처럼 객체를 계속 참조하는 요소를 사용이 끝났을 때 정리합니다.

### 코드와 데이터는 메모리의 어디에 저장되나요?

JavaScript 표준은 값의 실제 저장 위치를 정하지 않습니다. 일반적으로 함수 실행 정보는 호출 스택에서, 객체·배열·함수 객체는 엔진의 힙에서 관리된다고 설명하지만, 실제 위치는 엔진 최적화에 따라 달라질 수 있습니다.

### 참조를 끊으면 메모리가 바로 해제되나요?

아닙니다. 참조를 끊으면 객체가 가비지 컬렉터의 회수 대상이 될 수 있을 뿐이고, 실제 메모리 해제 시점은 엔진이 결정합니다. 다른 참조가 남아 있으면 객체는 계속 유지됩니다.

### 클로저가 메모리에 영향을 주는 이유는 무엇인가요?

클로저는 바깥 함수가 끝난 뒤에도 바깥 함수의 변수를 사용할 수 있게 합니다. 그래서 반환된 함수가 큰 객체까지 참조하면 그 객체가 오래 유지될 수 있습니다. 필요한 값만 클로저가 참조하도록 주의해야 합니다.

브라우저 프로세스, DOM·이미지·Canvas·GPU 메모리, Chrome 작업 관리자와 Heap Snapshot은 [브라우저 메모리 구조와 관리](/blog/javascript-memory-process-thread)에서 설명합니다.

- V8의 세부 GC 방식과 최적화는 버전에 따라 달라질 수 있습니다.
