## 요약

JavaScript에서 객체·배열·함수는 V8의 JS 힙에 저장되고, 변수에는 해당 값을 가리키는 참조가 저장됩니다. JavaScript 엔진은 전역 객체와 현재 실행 중인 함수처럼 계속 접근할 수 있는 지점에서 참조를 따라가며, 더 이상 도달할 수 없는 객체를 GC 대상으로 판단합니다. 개발자가 `free()`처럼 객체를 직접 해제하는 것이 아니라, 참조를 끊어 GC가 회수할 수 있는 상태를 만드는 구조입니다.

클로저·전역 변수·계속 커지는 캐시·해제하지 않은 이벤트 리스너는 필요하지 않은 객체를 계속 도달 가능한 상태로 만들 수 있습니다. 특히 SPA에서는 페이지가 닫히지 않고 화면만 바뀌기 때문에, 컴포넌트가 제거될 때 리스너·타이머·WebSocket·Worker 같은 리소스를 cleanup해야 합니다. 브라우저 프로세스·DOM·이미지·Canvas·GPU·캐시의 구조와 관리는 [브라우저 메모리 구조와 관리](/blog/javascript-memory-process-thread)에서 설명합니다.

> **핵심:** JavaScript는 객체를 직접 해제하지 않고, 참조가 끊겨 도달할 수 없어진 객체를 GC가 회수합니다. 개발자는 리스너·타이머·연결·캐시처럼 참조를 오래 유지하는 요소를 생명주기에 맞게 정리해야 합니다.

## Deep Dive

### 1. 메모리 생명주기

JS는 C와 달리 `malloc`/`free`를 직접 호출하지 않는다. 대신 3단계가 자동으로 돌아간다.

1. **할당**: 값을 만들 때 엔진이 자동으로 메모리 확보 (객체 리터럴, 배열, 함수, 문자열 등)
2. **사용**: 읽기·쓰기
3. **해제**: 더 쓰이지 않으면 GC가 자동 회수

```js
let user = { name: "건우" }; // 할당 (V8 힙에 객체 생성)
console.log(user.name); // 사용
user = null; // 참조 제거 → 다음 GC 때 회수 대상
```

개발자가 직접 하는 건 "참조를 끊는 것"뿐이고, **실제 해제 시점은 GC가 결정**한다.

### 2. 값의 종류별 저장 방식

| 종류   | 예                                               | 저장 방식 (기본 모델)                                                              |
| ------ | ------------------------------------------------ | ---------------------------------------------------------------------------------- |
| 원시값 | number, boolean, null, undefined, bigint, symbol | 변수에 값 자체가 저장되는 기본 모델. 실제 위치는 엔진 최적화에 따라 달라질 수 있음 |
| 문자열 | `'abc'`                                          | V8 힙. 상수 문자열은 공유·인터닝될 수 있음                                         |
| 객체   | `{}`, `[]`, 함수, Map, Set                       | 항상 V8 힙. 변수에는 **참조(포인터)**만 저장                                       |

- 원시값은 **불변**이라 복사하면 값이 복사된다.
- 객체는 **참조가 복사**돼서 같은 객체를 여러 변수가 가리킬 수 있다.

```js
const a = { v: 1 };
const b = a; // 객체가 복사된 게 아니라 참조만 복사
b.v = 2;
console.log(a.v); // 2
```

(스택/힙 위치는 엔진 최적화에 따라 달라질 수 있는 기본 모델이다.)

### 3. 가비지 컬렉션 (GC)

#### 3-1. 회수 기준: 도달 가능성

"쓰고 있는가"가 아니라 **"루트에서 참조를 따라 도달할 수 있는가"**가 기준이다.

- **루트**: 전역 객체, 현재 실행 중인 함수의 지역 변수(스택), 레지스터 등
- 루트에서 참조 체인으로 닿으면 살아 있음, 닿지 못하면 회수

```js
let a = { name: "A" };
let b = { friend: a };
a = null; // b.friend가 아직 가리키므로 객체 A는 살아 있음
b = null; // 이제 도달 불가 → 둘 다 회수 대상
```

서로를 참조하는 **순환 참조**도 루트에서 닿지 않으면 회수된다. (예전 참조 카운팅 방식과의 차이점)

#### 3-2. Mark-and-Sweep

1. **Mark**: 루트에서 출발해 도달 가능한 객체에 표시
2. **Sweep**: 표시되지 않은 객체의 메모리 해제 (필요 시 compaction으로 단편화 정리)

#### 3-3. V8은 GC 부담을 줄인다

대부분의 객체는 짧게 사용되고 사라진다는 특성을 이용해, V8은 새 객체와 오래 살아남은 객체를 나누어 관리한다. 새 객체가 있는 영역은 자주 정리하고, 오래 살아남은 객체가 있는 영역은 덜 자주 정리해 전체 작업량을 줄인다.

GC가 메모리를 정리하는 동안 JavaScript 실행이 잠깐 멈출 수 있다. V8은 정리 작업을 여러 번에 나누거나 다른 스레드와 나누어 처리해 이 멈춤 시간을 줄이지만, 개발자가 GC 실행 시점이나 멈춤 시간을 직접 지정할 수는 없다.

#### 3-4. 개발자가 제어할 수 없는 것

- GC **실행 시점**은 엔진이 결정한다. 코드로 강제할 수 없다.
- `null` 대입은 "참조를 끊는" 것이지 "즉시 해제"가 아니다.
- DevTools의 수동 GC 버튼은 디버깅용이다.

### 4. 클로저와 메모리

클로저는 **바깥 함수의 변수를 계속 참조**해서, 함수가 끝나도 그 변수가 힙의 별도 환경에 남는다. 스택 프레임은 함수 종료 시 사라지지만, 반환된 함수가 계속 써야 하므로 힙에 둬야 하기 때문이다.

```js
function createCounter() {
  let count = 0;
  const bigData = new Array(1_000_000).fill(0);
  return () => ++count; // count를 캡처
}
const counter = createCounter();
```

- 반환된 함수가 살아 있는 동안 캡처된 변수는 회수되지 않는다.
- V8은 보통 **실제로 쓰이는 변수만** 클로저 환경에 담아서, 위 예시의 `bigData`는 대개 캡처되지 않는다. 다만 같은 스코프의 다른 클로저가 쓰거나 `eval` 등이 있으면 함께 남을 수 있다. (엔진 구현에 따라 다름)
- 큰 객체를 클로저가 우연히 붙잡는 게 대표적인 누수 패턴이다.

### 5. 메모리 누수 패턴

누수 = **필요 없는데 아직 도달 가능한 객체**.

| 패턴          | 원인                                                 | 해결                                         |
| ------------- | ---------------------------------------------------- | -------------------------------------------- |
| 전역 변수     | 의도치 않은 전역(선언 누락 등)이 계속 살아 있음      | `const`/`let` 사용, strict mode, 모듈 스코프 |
| 이벤트 리스너 | `window`/`document` 등 수명 긴 대상에 등록 후 미해제 | `removeEventListener`                        |
| 타이머        | `setInterval`/`setTimeout` 콜백이 참조 유지          | `clearInterval`/`clearTimeout`               |
| detached DOM  | DOM에서 제거했지만 JS 변수·배열이 참조               | 참조 해제 (`null`, 컬렉션에서 제거)          |
| 커지는 캐시   | `Map`/배열/객체에 계속 추가만 함                     | 크기 제한, 오래된 항목 제거                  |
| 클로저        | 콜백이 큰 객체를 캡처                                | 필요한 값만 캡처, 사용 후 참조 해제          |
| 연결·워커     | WebSocket, Worker, 구독 미종료                       | `close()`, `terminate()`, `unsubscribe()`    |
| Blob URL      | `createObjectURL` 후 미해제                          | `URL.revokeObjectURL()`                      |
| 미완료 비동기 | 끝나지 않는 Promise/fetch가 실행 환경을 유지         | 취소하거나 완료 후 참조 정리                 |

**참고**: 페이지를 닫거나 이동하면 브라우저가 전부 정리한다. 문제가 되는 건 **SPA처럼 페이지는 유지되는데 컴포넌트만 사라지는 경우**라서, 언마운트 시점의 cleanup이 중요하다.

```js
// React 예시: cleanup으로 누수 방지
useEffect(() => {
  const onResize = () => {
    /* ... */
  };
  window.addEventListener("resize", onResize);
  const id = setInterval(tick, 1000);
  const socket = new WebSocket(url);

  return () => {
    window.removeEventListener("resize", onResize);
    clearInterval(id);
    socket.close();
  };
}, []);
```

### 6. 메모리를 아끼는 실무 습관 (상황·이유·효과)

#### 6-1. 큰 객체를 전역/모듈 스코프에 오래 두지 않기

**어떤 상황**

- 앱 전체에서 쓰려고 큰 데이터(API 응답 전체, 검색 인덱스, 큰 배열)를 모듈 최상단 변수에 담아둘 때
- 화면에서는 이미 안 쓰는데 변수는 계속 남아 있을 때

**왜 문제인가**

- 전역·모듈 변수는 **루트에서 항상 도달 가능**해서 GC가 회수하지 못한다. 탭이 살아 있는 동안 계속 메모리를 차지한다.
- SPA는 페이지를 안 닫고 화면만 바꾸므로, 쌓인 데이터가 탭이 닫힐 때까지 남는다.

```js
// 나쁜 예: 모듈 스코프에 영구 보관
const allPosts = [];
export async function load() {
  allPosts.push(...(await fetchAllPosts())); // 호출할 때마다 계속 쌓임
}

// 좋은 예: 함수/컴포넌트 스코프에서 쓰고, 끝나면 참조가 사라지게
export async function load() {
  const posts = await fetchAllPosts();
  return render(posts); // 함수가 끝나면 posts는 도달 불가 → 회수
}
```

**좋아지는 것**: 화면을 벗어난 데이터가 자동 회수돼 탭의 메모리 기준선이 올라가지 않는다.

#### 6-2. 큰 데이터는 사용 후 참조 해제, 컬렉션은 크기 제한

**어떤 상황**

- 로그, 채팅 메시지, 실시간 시세처럼 **계속 들어오는 데이터**를 배열/Map에 push만 할 때
- 큰 임시 데이터(파싱 결과, 업로드한 파일 내용)를 다 쓰고도 변수에 들고 있을 때

**왜 문제인가**

- 배열·Map은 **빼지 않으면 계속 커진다.** 가장 흔한 누수 패턴이 "커지는 캐시"다.
- 큰 데이터는 변수가 참조하는 한 GC가 가져가지 못한다.

```js
// 최대 길이 제한 (오래된 것부터 제거)
const MAX = 500;
function addLog(entry) {
  logs.push(entry);
  if (logs.length > MAX) logs.shift();
}

// 다 쓴 큰 데이터는 참조 끊기
let bigData = parseHugeFile(file);
process(bigData);
bigData = null; // 이후 GC가 회수 가능

// 캐시 상한 (Map은 삽입 순서를 유지하므로 가장 오래된 키 삭제 가능)
if (cache.size > 100) cache.delete(cache.keys().next().value);
```

**좋아지는 것**: 메모리 사용량에 **상한**이 생겨서, 오래 켜둬도 무한정 증가하지 않는다.

#### 6-3. 불필요한 객체 생성을 줄여 GC 부담 감소

**어떤 상황**

- 스크롤, 애니메이션(`requestAnimationFrame`), 마우스 이동, 대량 루프처럼 **1초에 수십~수만 번 실행되는 코드**
- 그 안에서 매번 새 객체·배열·클로저·문자열을 만들 때

**왜 문제인가**

- 만든 객체가 곧 쓰레기가 되면 GC가 자주 실행되어 정리 작업이 늘어난다.
- GC가 실행되는 동안 JavaScript가 잠깐 멈출 수 있어 스크롤이나 애니메이션이 끊길 수 있다.
- 누수는 아니지만 메모리 그래프가 톱니처럼 오르내리고 성능이 떨어진다.

```js
// 나쁜 예: 프레임마다 객체/배열 새로 생성
function onFrame() {
  const pos = { x: getX(), y: getY() };
  const items = list.map((i) => ({ ...i, active: true })); // 매 프레임 복사
  draw(pos, items);
}

// 좋은 예: 재사용 가능한 건 밖에서 한 번만 만들고 값만 갱신
const pos = { x: 0, y: 0 };
function onFrame() {
  pos.x = getX();
  pos.y = getY();
  for (const i of list) draw(pos, i); // 중간 배열 생성 없이 순회
}
```

- 루프 안의 `map/filter/spread` 체이닝은 중간 배열을 만든다. 스크롤이나 애니메이션처럼 자주 실행되는 코드에서만 `for` 루프나 객체 재사용을 고려한다.

**좋아지는 것**: GC 횟수와 정지 시간이 줄어 **프레임 안정성**이 좋아진다.

**주의**: 모든 코드를 이렇게 최적화할 필요는 없다. **측정(Performance, Allocation sampling)으로 병목을 확인한 곳**에만 적용해야 가독성을 해치지 않는다.

#### 6-4. 대용량 처리는 스트림·청크 단위로

**어떤 상황**

- 수십~수백 MB 파일 업로드·다운로드, 큰 CSV/JSON 파싱, 큰 응답 처리
- 전체를 한 번에 읽어 메모리에 올린 뒤 처리할 때

**왜 문제인가**

- 전체를 메모리에 올리면 **데이터 크기만큼** 순간 메모리가 필요하다. (변환·복사 과정에서 2~3배가 될 수도 있음)
- 모바일이나 저사양 기기에서는 메모리 부족으로 탭이 크래시하거나 폐기될 수 있다.

```js
// 나쁜 예: 전체를 한 번에 메모리로
const text = await (await fetch(url)).text();
const rows = JSON.parse(text);

// 좋은 예: 스트림으로 조각씩 처리
const res = await fetch(url);
const reader = res.body.getReader();
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  handleChunk(decoder.decode(value, { stream: true })); // 조각 처리 후 버려짐
}

// 파일은 slice로 나눠서 업로드/처리
const CHUNK = 5 * 1024 * 1024;
for (let start = 0; start < file.size; start += CHUNK) {
  await upload(file.slice(start, start + CHUNK));
}
```

**좋아지는 것**: 메모리 사용량이 **전체 크기가 아니라 청크 크기**로 고정돼요. 첫 데이터를 빨리 처리할 수 있어 체감 속도도 좋아진다.

#### 6-5. 이벤트 리스너를 수명에 맞게 등록·해제

**어떤 상황**

- `window`, `document`, `body`처럼 **페이지가 살아 있는 동안 계속 존재하는 대상**에 리스너를 붙일 때 (resize, scroll, keydown 등)
- 컴포넌트가 마운트될 때마다 등록하는데 해제는 안 할 때
- 한 번만 실행하면 되는 이벤트일 때

**왜 문제인가**

- 대상이 사라지지 않으므로 리스너와 그 콜백이 캡처한 변수·DOM도 **계속 도달 가능**하다.
- 컴포넌트를 열고 닫을 때마다 리스너가 **누적**돼서 이벤트 한 번에 콜백이 여러 번 실행되고 메모리도 늘어난다.
- 반면 **제거되는 DOM 요소 자신**에 붙인 리스너는 요소가 회수될 때 함께 회수되므로 상대적으로 안전하다.

```js
// 1) 한 번만 필요하면 once
button.addEventListener("click", handler, { once: true });

// 2) React: cleanup 함수
useEffect(() => {
  window.addEventListener("resize", onResize);
  return () => window.removeEventListener("resize", onResize);
}, []);
```

**좋아지는 것**: 리스너가 쌓이지 않아 **누수와 중복 실행을 방지**하고, 해제 코드가 한 줄로 줄어 **실수가 감소**한다.

**추가 팁**: 목록 항목마다 리스너를 붙이는 대신 부모에 하나만 붙이는 **이벤트 위임**을 쓰면 리스너 수 자체가 줄어든다.

#### 6-6. JS 힙 밖 네이티브 메모리를 쓰는 객체는 참조까지 끊기

**어떤 상황**

- 큰 이미지(`Image`, `ImageBitmap`), `Canvas`, `Blob`, `ArrayBuffer`, `URL.createObjectURL()`, 동영상, `OffscreenCanvas` 등을 다룰 때
- 이미지 미리보기, 파일 업로드, 캔버스 편집기, 지도·차트 라이브러리 등

**왜 문제인가**

- JS 쪽에는 **작은 래퍼 객체**만 있고, 실제 데이터(디코딩된 픽셀, 바이너리 버퍼, GPU 텍스처)는 **JS 힙 밖 네이티브 메모리**에 있다.
- 그래서 **JS 힙은 작은데 탭 전체 메모리(Memory footprint)는 큰** 상황이 생기고, Heap Snapshot만 보면 놓치기 쉽다.
- 래퍼 참조가 남아 있으면 그 뒤의 큰 네이티브 메모리도 함께 풀리지 않는다.
- `createObjectURL`은 `revoke`하기 전까지 브라우저가 Blob을 **계속 유지**한다.

```js
// Blob URL: 쓰고 나면 해제
const url = URL.createObjectURL(file);
img.src = url;
img.onload = () => URL.revokeObjectURL(url); // 로드 후 해제

// ImageBitmap: close()로 명시적 해제
const bitmap = await createImageBitmap(blob);
ctx.drawImage(bitmap, 0, 0);
bitmap.close(); // 네이티브 메모리 즉시 반환

// Canvas: 더 안 쓰면 크기를 0으로 줄이고 참조 제거
canvas.width = 0;
canvas.height = 0;
canvas = null;

// 큰 이미지는 표시 크기에 맞게 축소해서 사용 (원본 그대로 올리지 않기)
```

**좋아지는 것**: JS 힙에는 안 보이지만 **전체 메모리의 큰 비중**을 차지하는 부분이 제때 반환된다. 이미지가 많은 페이지에서 효과가 가장 크다.

#### 6-7. 한눈에 보는 표

| 습관                                 | 이런 상황에서               | 안 하면                             | 하면                    |
| ------------------------------------ | --------------------------- | ----------------------------------- | ----------------------- |
| 전역/모듈 스코프에 큰 객체 두지 않기 | 앱 전역 데이터 보관         | 탭 종료까지 회수 안 됨              | 화면 벗어나면 자동 회수 |
| 사용 후 참조 해제, 크기 제한         | 로그·메시지·캐시 누적       | 무한 증가                           | 사용량 상한 확보        |
| 불필요한 객체 생성 줄이기            | 스크롤·애니메이션·대량 루프 | GC 잦아져 버벅임                    | 프레임 안정             |
| 스트림·청크 처리                     | 대용량 파일·응답            | 데이터 크기만큼 메모리 급증, 크래시 | 청크 크기로 고정        |
| 리스너 수명 관리                     | window/document 이벤트, SPA | 리스너 누적, 중복 실행, 누수        | 누수 방지, 정리 간단    |
| 네이티브 메모리 참조 끊기            | 이미지·Canvas·Blob          | JS 힙은 작은데 탭이 무거움          | 전체 메모리 감소        |

#### 6-8. 적용 우선순위

1. **먼저 측정**: 7번의 방법으로 실제로 메모리가 늘어나는지 확인한다.
2. **누수성 문제(6-1, 6-2, 6-5, 6-6)부터**: 시간이 갈수록 쌓이는 문제라 영향이 크다.
3. **성능성 문제(6-3, 6-4)는 병목이 확인된 곳에만**: 측정 없이 미리 최적화하면 코드만 복잡해질 수 있다.

### 7. 진단 방법 (Chrome DevTools)

#### 7-0. 준비

- **production build에서 측정**하는 게 좋다. 개발 모드의 React DevTools, HMR, 개발 오버레이가 메모리에 섞이기 때문이다.
- 측정 동작은 실제 사용 시나리오로 정한다. (페이지 이동, 검색 열기·닫기, 코드 복사, 새로고침·뒤로 가기 등)

```bash
npm run build
npm run start     # 빌드 결과로 서버 실행 후 해당 페이지 열기
```

#### 7-1. Task Manager: 전체 메모리 확인

1. `Shift + Esc`로 Chrome Task Manager 열기 (DevTools가 아니라 Chrome 기능)
2. 표 헤더 우클릭 → **JavaScript memory** 활성화
3. 현재 탭의 값 확인

| 항목              | 의미                                                                      |
| ----------------- | ------------------------------------------------------------------------- |
| Memory footprint  | JS 힙 + DOM + 이미지 등 **탭 전체 메모리**                                |
| JavaScript memory | **JS 힙**. 괄호 밖은 현재 할당된 크기, 괄호 안은 GC 후에도 살아 있는 크기 |

- 같은 페이지에서 새로고침, 검색 열기·닫기, 다른 글 이동을 반복한다.
- 괄호 안의 JS 메모리나 전체 메모리가 **계속 올라가고 내려오지 않으면** 누수를 의심한다.
- Footprint만 크고 JS memory는 작다면 이미지·Canvas 같은 네이티브 메모리를 의심한다. (6-6)

#### 7-2. Heap Snapshot: 객체와 detached DOM 확인

**여는 법**: F12 (macOS는 `⌘ + Option + I`) → 우측 상단 ⋮ → More tools → **Memory** → **Heap snapshot** 선택

**절차**

1. **Take snapshot**으로 기준 스냅샷 1을 찍는다.
2. 테스트 동작을 10~20회 반복한다. (목록 ↔ 상세 이동, 검색 열기·닫기, 코드 복사 등)
3. 스냅샷 2를 찍는다.
4. 스냅샷 2를 선택하고 보기 방식을 **Comparison**으로 바꾼다.
5. 새로 생긴 객체와 계속 남아 있는 객체를 확인한다.
6. 검색창에 `Detached`를 입력한다.
7. 의심 객체를 클릭하고 하단 **Retainers**에서 누가 붙잡고 있는지 확인한다.

**해석**

- Detached DOM이 남아 있다면 화면에서는 제거됐지만 **JS 참조가 붙잡고 있는 상태**다.
- Retainers 경로(예: 전역 변수 → 배열 → 객체 → DOM)가 곧 **끊어야 할 참조**다.
- 스냅샷 전에 수동 GC(Performance 탭의 Collect garbage 버튼)를 실행하면 아직 회수되지 않았을 뿐인 객체를 걸러낼 수 있다.

#### 7-3. Allocation sampling: 메모리를 많이 만든 함수 찾기

"어떤 함수가 메모리를 많이 할당했나"를 보는 도구다.

1. Memory 탭 → **Allocation sampling** 선택 → **Start**
2. 의심되는 동작을 반복 (예: 코드 복사 버튼 20번)
3. **Stop**
4. 결과에서 **Heavy (Bottom Up)** 확인

- 특정 함수가 계속 상위에 보이면, 그 함수가 반복적으로 객체·문자열을 만드는지 코드를 확인한다. (7-3과 연결)
- 장시간 동작에도 비교적 부담이 적다.
- "얼마나 남았나"가 아니라 "누가 할당했나"를 보는 용도다. 누수 확인은 Heap Snapshot이 맞다.

#### 7-4. Performance: 시간 흐름 확인

1. Performance 탭 → **Memory** 체크 → 녹화 시작
2. 페이지 이동·검색·코드 복사 등을 반복
3. 녹화 종료

| 그래프 항목 | 볼 것            |
| ----------- | ---------------- |
| JS Heap     | JS 메모리 추이   |
| Nodes       | DOM 노드 수      |
| Listeners   | 이벤트 리스너 수 |
| Documents   | 문서 수          |
| GPU memory  | GPU 메모리       |

- 시작과 끝에 **Collect garbage**(휴지통 아이콘)로 강제 GC를 실행하면 비교하기 쉽다.
- **정상**: 동작 → 메모리 증가 → GC → 다시 감소
- **누수 의심**: 동작 → 증가 → GC 후에도 이전보다 높음, 반복할수록 기준선이 계속 상승
- Nodes나 Listeners가 페이지 이동을 반복할수록 계속 늘면 리스너·DOM 정리 문제를 의심한다.

#### 7-5. 추천 측정 순서

```text
Task Manager (전체/JS 메모리 추이 확인)
→ Heap Snapshot 1 (기준)
→ 동작 10~20회 반복
→ Heap Snapshot 2
→ Comparison / Detached / Retainers 확인
→ Allocation sampling으로 원인 함수 확인
→ Performance Memory로 시간 흐름 확인
```

처음에는 **Heap Snapshot 두 개 비교**만 해도 충분하다.

#### 7-6. 누수 확인 요약 절차

1. 시작 상태를 맞추고 수동 GC 후 스냅샷 1
2. 의심 동작을 여러 번 반복
3. 수동 GC 후 스냅샷 2
4. Comparison에서 **계속 늘어나는 객체**와 **Retainers**(붙잡고 있는 경로) 확인

GC 타이밍 때문에 힙 크기만 보면 오판하기 쉬워서, **수동 GC 후 비교**가 핵심이다.

### 8. 브라우저 메모리 구조 문서와의 구분

|           | 브라우저 메모리 구조 문서                      | 이 문서 (JS 메모리 관리)                              |
| --------- | ---------------------------------------------- | ----------------------------------------------------- |
| 관점      | 메모리가 **어디에** 있는가                     | 메모리를 **어떻게 쓰고 해제하는가**                   |
| 층위      | OS(프로세스·스레드) → V8 → JS 개념             | JS 코드 수준 (V8 GC 포함)                             |
| 핵심      | 프로세스/스레드, 스택·힙·mmap, V8 힙·코드 영역 | 생명주기, 도달 가능성, GC, 누수 패턴, 실무 습관, 진단 |
| 연결 고리 | V8 힙(GC 대상)                                 | 그 V8 힙을 자동으로 정리하는 방식                     |

## 참고

- V8 기준이며 SpiderMonkey(Firefox), JavaScriptCore(Safari)는 GC 세부 구현이 다르다. (도달 가능성 기반이라는 원리는 공통)
- 원시값/객체의 스택·힙 저장 위치는 개념 이해용 기본 모델이고, 실제로는 엔진 최적화에 따라 달라질 수 있다.
- 클로저 캡처 범위, GC 영역 구성(Young/Old 세부 구조) 등은 V8 버전에 따라 달라질 수 있다.
- 코드 예시는 개념 설명용이며, 실제 효과는 엔진 최적화·데이터 크기·브라우저에 따라 달라질 수 있다.
- `bigData = null` 같은 참조 해제는 "즉시 해제"가 아니라 "GC가 회수 가능하게 만드는 것"이다.
- `ImageBitmap.close()` 같은 API 지원 여부와 DevTools 메뉴 이름·위치는 브라우저와 버전에 따라 다를 수 있으니 사용 전에 확인한다.
