# 개발자 포트폴리오 설계안

작성일: 2026-09-12
상태: 콘텐츠 작성, 페이지 구현과 로컬 검증 완료. 공개 배포 전.
작업 브랜치: `feature/portfolio-page`

## 1. 제출 방식

포트폴리오 URL을 요구하는 지원에는 전용 `/portfolio` 페이지를 제출하고, 페이지에서 동일한 내용의 통합 PDF를 내려받게 하는 구성을 권장한다. URL 요구가 자체 개발 사이트를 의미하지는 않는다. 마감이 가까우면 제출용으로 정리한 공개 Notion 페이지 또는 공고에서 허용하는 공개 PDF 링크를 먼저 사용할 수 있다.

공고 원문과 마감일은 아직 확인하지 않았다. 파일 형식·용량·외부 링크 허용 여부는 해당 공고의 제출 조건을 우선한다. 예정 주소는 `https://www.pigpgw.cloud/portfolio`이며 현재 배포된 주소로 간주하지 않는다.

현재 자료 판단:

| 자료 | 확인한 내용 | 활용 방식 |
| --- | --- | --- |
| Developer Notion | 전체 경험, 프로젝트별 상세 구현, 작성 기준과 보조 기록 | 사실 확인과 콘텐츠 작성 원천 |
| `1.pdf` | 경력·프로젝트·교육·수상·학력을 모은 이력서 1장 | 별도 이력서로 유지 |
| `2.pdf` | 다중 Agent 구조, AI 활용 퍼블리싱 프로세스 | CPPM과 프비티 사례로 각각 배치 |
| `3.pdf` | Trace 진행 상태 UI, SQS 비동기 구조 | CPPM의 핵심 문제 해결 사례 |
| `4.pdf` | 채팅 검색, API Key 격리와 XSS 대응 | CPPM 상세의 보조 사례 |

`2~4.pdf`는 문제·해결·결과와 도식이 있어 좋은 원자료다. 다만 회사·프로젝트 개요와 개인 역할이 충분히 드러나지 않고 Code Sync 상세가 없다. 네 파일을 그대로 나열하기보다 프로젝트별 흐름으로 재구성한다. Notion 원장에는 개인 정보와 작성용 메모가 있어 원장 자체보다 별도 제출본이 적합하다.

## 2. 범위와 포지셔닝

두 경험군, 세 프로젝트로 구성한다.

- 실무: 디지엠 유닛원 / CPPM, 프비티
- 교육 최종 프로젝트: 크래프톤 정글 6기 / Code Sync

SKALA, 대학 연구, 다른 사이드 프로젝트와 정글 CS 학습 상세는 이번 포트폴리오에서 제외한다. 이력서 링크에서 전체 이력을 확인하게 한다.

소개 초안:

> 박건우 | Developer
>
> 실시간 협업부터 AI 업무지원까지, 복잡한 사용자 흐름을 화면·API·상태로 구현해 온 개발자입니다.

대표 사례 순서는 사용자의 최신 정정에 따라 CPPM → 프비티 → Code Sync로 확정한다. 설계와 구현 근거가 풍부한 CPPM을 먼저 보여주고 크래프톤 정글 최종 프로젝트는 마지막에 둔다. 웹 목록·다음 프로젝트 이동·PDF에 같은 순서를 적용한다. 영문 이름은 Park Geon Woo로 표기한다.

## 3. URL과 읽기 흐름

| 경로 | 역할 |
| --- | --- |
| `/portfolio` | 제출 URL. 소개, 대표 사례 3개, 이력서·PDF·GitHub·연락처 |
| `/portfolio/cppm` | LG 공통업무 플랫폼의 AI 업무지원 사례 |
| `/portfolio/code-sync` | 크래프톤 정글 최종 프로젝트의 실시간 코드리뷰 사례 |
| `/portfolio/fbiti` | 프랜차이즈 업무 화면과 서비스 분리 사례 |
| `/resume` | 기존 이력서 유지 |

첫 화면에서 이름, 구현 분야, 첫 프로젝트의 실제 화면 또는 구조도를 볼 수 있게 한다. 프로젝트 목록에는 서비스 설명, 소속, 본인 역할, 대표 해결 내용, 상세 링크를 표시한다. 경력 전체나 기술 로고 목록을 먼저 길게 배치하지 않는다.

상세 공통 순서:

1. 프로젝트명·서비스 설명·기간·소속·역할·직접 사용한 핵심 기술
2. 실제 화면 또는 구조도와 본인 기여 요약
3. 핵심 문제 해결 2~3개: 상황 → 판단과 이유 → 구현 → 결과·검증
4. 보조 구현과 한계·회고
5. 공개 가능한 코드·발표·증빙 링크와 다음 프로젝트

서비스 전체 기능과 개인 기여를 구분한다. 팀 규모나 기여율은 확인되지 않았으므로 임의로 넣지 않는다. 기술 선택 이유와 회고도 원문 근거가 없으면 작성자의 확인이 필요한 초안으로 둔다.

## 4. CPPM 상세 초안

설명: LG 그룹 공통업무 플랫폼에서 사내 사용자의 데이터 조회·분석·그래프 생성을 돕는 AI 업무지원 기능.
소속: 디지엠 유닛원 실무. 회사 재직 기간은 2025.07~2026.01이며 프로젝트별 기간은 원문 재확인 후 확정한다.

### 사례 A. 장시간 작업과 요청 수신 분리

- 상황: 1~2분 걸리는 Agent 작업을 요청 Lambda에서 기다리면서 API Gateway WebSocket 통합 요청이 타임아웃됐다.
- 구현: 요청 Lambda에서 connectionId와 요청을 SQS에 적재하고 즉시 반환한다. Event Source Mapping으로 호출되는 Worker Lambda가 작업을 수행하고 Management API의 `PostToConnection`으로 응답과 Trace를 전달한다.
- 결과: 요청 수신과 장시간 처리를 분리하고 처리 단계를 화면에 제공했다.
- 시각 자료: `3.pdf`의 전후 구조도와 진행 상태 화면. 웹에서는 글자가 읽히는 크기로 개별 배치한다.
- 표현 기준: 통합 요청 타임아웃과 WebSocket 연결 종료는 동일한 현상으로 단정하지 않는다. Trace의 대기 불확실성 개선과 실제 처리시간 단축도 구분한다.

### 사례 B. 다중 Agent와 검색 신뢰성

- 상황: 단일 Agent에 일반 대화·조회·그래프 생성 규칙이 집중되고 검색 실패 후 재검색과 근거 없는 응답이 발생했다.
- 구현: Master·Supervisor·전문 Agent 역할과 Knowledge Base를 분리하고 결과 없음·오류·재시도의 종료 규칙을 구성했다.
- 결과: 역할별 규칙·지식 관리와 검색 실패 처리 흐름을 분리했다.
- 시각 자료: `2.pdf`의 Agent 구조도. 서비스 제공 기능과 본인이 구성한 라우팅·검증 규칙을 설명한다.

### 사례 C. 검색에서 이전 메시지 이동까지

- 상황: 로드되지 않은 대화는 브라우저 기본 검색으로 찾을 수 없었다.
- 구현: ERD·REST API·검색 UI, 하이라이팅과 메시지 이동, 300ms debounce, `LastEvaluatedKey` 기반 20개 단위 조회를 연결했다.
- 결과: 이전 대화를 검색하고 해당 채널·메시지로 이동하는 흐름을 구현했다.
- 시각 자료: `4.pdf` 검색 화면. 실제 캡처인지 설명용 재구성인지 확인해 캡션을 붙인다.

API Key 서버 격리, DOMPurify 정제, 이벤트 구독 해제와 테스트는 보조 구현에 배치한다. 테스트 커버리지 80% 이상은 기록에 있으나 리포트·대상·시점 확인 전 대표 수치로 강조하지 않는다.

## 5. Code Sync 상세 초안

설명: GitHub PR을 기반으로 화상 대화와 실시간 편집을 연결하는 코드리뷰 협업 플랫폼.
소속: 크래프톤 정글 6기 최종 프로젝트.
기간: 2024.10.11~2024.11.16. 역할: Frontend Engineer.

### 사례 A. 같은 코드와 위치를 보며 리뷰하기

- 상황: 참여자가 서로 다른 파일과 커서 위치를 보면서 리뷰 맥락을 맞추기 어려웠다.
- 구현: Yjs와 Monaco Editor를 연동하고 현재 파일·커서 공유, 상대방 파일 이동, 파일 전환 시 Awareness와 리스너 정리를 구현했다.
- 결과: 코드와 위치를 공유하고 상대방의 리뷰 맥락으로 이동하는 흐름을 구성했다.
- 시각 자료: 실제 두 참여자 화면의 동기화 캡처 또는 짧은 영상. 현재 PDF에는 없으므로 공개 저장소·발표 자료에서 확보해야 한다.

### 사례 B. PR 조회 안정성과 중복 요청

- 브랜치 삭제 후 파일 조회 실패: `head.sha`·`base.sha` 기준 commit snapshot 조회로 전환했다.
- 참여자별 중복 요청: Host가 조회한 파일·댓글·PR 정보를 Y.Doc으로 공유했다.
- 기록된 결과: GitHub API 호출 44회 → 22회. 참여자 수·PR 조건과 측정 범위를 함께 확인해 표기한다.
- 시각 자료: Host 조회 → 공유 상태 → Guest 수신 구조와 본인 코드 링크.

### 사례 C. 초기 로드 범위 축소

- 상황: 첫 진입에 필요하지 않은 화면 코드까지 포함된 초기 번들 구조.
- 구현: route 단위 code splitting과 lazy loading 적용.
- 기록된 결과: 초기 JS 번들 1,820KB → 99KB. 당시 측정 기록으로 표시하며 서비스 전체 용량이나 현재 빌드 결과로 표현하지 않는다.

문서 협업·화이트보드·화면 캡처는 보조 구현으로 연결한다. PR 댓글 285→89, 불편 응답 50→5는 팀·설문 조건이 확인되기 전 대표 지표에 넣지 않는다. 댓글 감소만으로 코드 품질 향상을 주장하지 않는다.

## 6. 프비티 상세 초안

설명: 프랜차이즈 본사의 CRM·멤버십·수발주·가맹점 운영을 통합 관리하는 서비스.
소속: 디지엠 유닛원 실무.

- 사용자별 화면: 고객 모바일의 콘텐츠·프로모션 참여·결과 확인과 가맹점 태블릿·본사 데스크톱 업무 흐름. 대표 화면과 담당 범위를 함께 제시한다.
- 서비스 분리: 36,238 LOC·300개 이상 파일·39개 API의 영향 범위와 의존성을 분석하고 영업관리·수발주 프로젝트 및 계정 흐름을 분리한 과정. 숫자는 개발 생산성 지표가 아니라 분석 범위다.
- 반복 퍼블리싱: Figma·공용 컴포넌트·접근성 기준을 Skill과 검증 절차로 정리한 과정. 4시간 이상 → 약 30분은 당시 반복 작업 기록으로 한정하고 프로젝트 전체 생산성으로 확대하지 않는다.

시각 자료는 공개 가능한 실제 사용자별 화면과 개념 수준의 분리 전후 구조를 우선한다. 리뷰 응답 자동화는 보조 구현으로 둔다.

## 7. 시각·구현 방향

현재 블로그의 화이트·차콜·코발트 포인트와 Pretendard를 계승한다. 프로젝트를 큰 카드 안에 모두 넣지 않고 구분선과 여백으로 나눈다. 실제 화면·구조도를 주된 시각 자료로 사용하고 장식용 이미지는 추가하지 않는다.

- 데스크톱: 목록 최대 폭 약 1120px, 상세 본문 약 760px, 도식은 넓게 표시. 상세에는 섹션 목차 제공.
- 모바일: 한 열 배치, 제목 줄바꿈, 이미지 확대, 표·코드의 국소 스크롤. 목차가 본문을 가리지 않게 구성.
- 동영상은 자동 재생하지 않고 대표 이미지와 재생 동작 제공.
- 이미지에 대체 텍스트와 캡션을 제공하고 실제 캡처·설명용 재구성을 구분.
- 이력서, 통합 PDF, GitHub는 명확한 링크로 제공. 준비되지 않은 링크는 표시하지 않음.

구현 시 기존 App Router의 Server Component와 `src/content` 패턴을 활용한다. 사례 세 개는 로컬 콘텐츠로 관리하고, 별도 CMS·DB·인증·Notion 실시간 조회를 추가하지 않는다. 제출 사이트를 열 때 Notion 연결에 의존하지 않게 한다. 기존 공개 URL은 유지한다.

## 8. 자료 정합성과 제출 전 확인

| 항목 | 확인된 차이 또는 빈칸 | 처리 |
| --- | --- | --- |
| Agent 응답시간 | `2.pdf`는 약 2분→1분~1분30초, Notion 후반 정정은 약 2분→1분10초 | 측정 시점·질의 조건 확인 전 단일 대표 수치로 확정하지 않음 |
| 수발주 의존성 | `1.pdf`는 233→0, Notion은 식별·제거·치환 범위 중심 | 0곳 검증 근거 확인 전 분석 범위와 분리 산출물 중심 |
| 테스트 커버리지 | 80% 이상 기록, 상세 리포트 미확인 | 대상·시점 확인 후 수치 사용 |
| PDF 이미지 | 구조도·화면 이미지 존재 | 원본 해상도와 실제 화면/재구성 여부 확인 |
| Code Sync | 원장·이력서에 구현과 수치 존재, 상세 PDF 부재 | 실시간 UI·API 공유·번들 사례 보강 |
| 실무 자료 공개 | 원장에 비공개 자료 표기 | 공개 가능한 범위의 캡처 또는 익명화한 설명 도식 사용 |

통합 PDF는 이력서와 별도로 구성한다. 표지·요약 1장, CPPM 2~3장, Code Sync 2장, 프비티 1~2장 정도로 시작하되 실제 내용과 가독성을 기준으로 조정한다.

배포 후에는 로그인 없는 직접 접근, 모바일 가독성, 이미지·증빙 링크, PDF 다운로드와 인쇄, 페이지 메타데이터·공유 미리보기를 운영 URL에서 확인한다. 로컬 검증은 아래 구현 결과에 기록한다.

## 9. 최초 설계의 확인 범위

- Developer Notion을 다시 조회하고 대상 프로젝트와 최신 정정 내용을 확인했다.
- PDF 네 파일의 전체 텍스트와 각 1페이지의 Quick Look 렌더링을 확인했다.
- 기존 README, AGENTS, 로드맵, 프론트 디자인 문서와 현재 이력서 코드를 확인했다.
- `pdftotext`는 설치되어 있지 않아 실행 실패했고 `pypdf`로 텍스트를 읽었다.
- 원본 저장소 커밋, 측정 리포트, 지원 공고, 실제 배포 화면은 이번 설계에서 검증하지 않았다.
- 애플리케이션 코드·원본 PDF·Notion은 수정하지 않았다.

검증 결과:

| 검증 | 결과 |
| --- | --- |
| `npm run lint` | 통과 |

공고별 맞춤 검토, 공개 배포, 외부 링크의 로그인 없는 접근·공유 미리보기, 원본 커밋·성능 리포트 감사는 미실행이다. 공고가 없는 상태에서는 일반 개발자 제출용으로 구성한다. 원본 PDF·Notion과 기존 사용자의 변경사항은 수정하거나 되돌리지 않았다.

## 11. 사용자 정정 반영

이 항목은 최초 설계의 CPPM 사례 순서와 수치 보류 판단보다 우선한다.

- CPPM의 핵심은 AWS Bedrock Agent를 활용한 다중 에이전트 아키텍처 설계·최적화다. 목록 소개, 대표 이미지, 상세 제목과 첫 사례를 Master·Supervisor·OpenSearch·Graph Agent 구조 중심으로 변경했다.
- 후속 사례는 Trace 기반 대기 경험, SQS 비동기 분리, 채팅 검색, API Key·XSS 대응 순서로 구성했다. AgentEventManager와 requestAnimationFrame 등 사용자가 제공한 구체적 구현을 반영했다.
- 사용자의 최신 정정에 따라 평균 응답시간 약 2분 → 1분~1분 30초를 사용한다. 실제 처리시간과 Trace 기반 대기 경험은 구분한다.
- 프비티는 [공식 사이트](https://www.fbiti.co.kr/)를 검색·확인해 본사·가맹점·고객, 멤버십·수발주·재고·영업관리의 서비스 맥락을 보강했다. 공식 사이트의 전체 기능과 비용 절감 광고 수치를 개인 성과로 옮기지 않았다.
- Code Sync는 사용자 제공 `Group 36.png`, `Group 37.png`, `Group 38.png`, `스크린샷 2024-11-24 오후 11.24.13 1.png`를 확인해 갤러리에 배치했다. 원본은 가로 161~246px로 작은 이미지이며 원본 파일은 수정하지 않았다.
- 공개 저장소의 `a8149f27936576f15101038ca46c822cfa951aba`에서 `MainFrame.tsx`의 Awareness 등록·해제와 `src/apis/pr/pr.ts`의 commitHash 기반 조회 코드를 읽고 발췌·고정 링크를 추가했다. 전체 커밋의 개인 기여 감사나 원본 서비스 재실행은 수행하지 않았다.

- `ProjectArtifacts`는 새로 추가한 설계·프롬프트·Skill 증빙을 웹과 PDF에 동일하게 표시한다. 프롬프트는 Markdown, 기존 Code Sync 코드는 TypeScript로 문법 강조한다.

- 문장은 문제·직접 구현·결과가 드러나도록 정리한다. Yjs의 동기화·충돌 병합, MonacoBinding과 협업 에디터의 제공 기능을 직접 개발한 것으로 표현하지 않는다. 직접 기여는 파일별 연동, 상태 저장·복원, 화면 이동, 리스너 정리로 구분한다.
